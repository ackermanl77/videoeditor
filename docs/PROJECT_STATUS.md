# Project Status

## Architecture

```text
main.py (PySide6 QApplication entry point)
        |
        v
ui/  (MainWindow, TimelineWidget, PreviewPlayer, PropertiesPanel, MediaBinWidget, ExportDialog, RenderQueue)
        |  reads Project/Track/Clip directly, but every mutation goes
        |  through a Command object executed via core.history.History
        v
core/ (Project, Track, Clip, History/Commands, EditOps, FilterGraph, Effects, Exporter, RenderQueue,
       MediaProbe, Waveform, Subtitles, Autosave, Relink, Proxy, FrameRender, Stabilize, OutputColor)
        |
        v
FFmpeg / FFprobe (subprocess, via core/ffmpeg_utils.py)
```

`core/` is the entire editing model and the FFmpeg render pipeline, with **zero Qt/GUI dependencies** — every module under `core/` can be imported and unit-tested (see `tests/`) without a display, and the core unit tests run in seconds with nothing but the standard library installed. `ui/` only *reads* from `core` and issues `Command` objects (`core/commands.py`) through `core.history.History`, so every editing operation (add/move/trim/split/delete a clip, add/remove a track, change any clip property) is undoable by construction; the UI never mutates `Project`/`Track`/`Clip` directly outside of a `Command`.

The preview (`ui/preview_player.py`) and the export pipeline (`core/filter_graph.py` + `core/exporter.py`) are two independent renderers of the same `Project`, and they deliberately don't agree on everything: during playback the preview plays only the topmost active video clip through `QMediaPlayer` (no real-time multi-track alpha compositing; while paused, the optional **Accurate frame** view shows a frame rendered by the export engine itself, `core/frame_render.py`), while export always builds a full `-filter_complex` graph and renders the true composited timeline — transitions, opacity, fades, and text overlays included. This is a conscious simplicity/fidelity trade-off, not a bug; see [preview-playback/workflow.md](workflows/preview-playback/workflow.md).

`core/ffmpeg_utils.py` centralizes how `ffmpeg`/`ffprobe` are located (bundled next to a PyInstaller build, then system `PATH`, then the `imageio-ffmpeg` package as a last resort) so no other module has to know how the binary was found.

## Primary Entry Points

| Purpose | Entry point |
|---|---|
| Desktop application | `python main.py` |
| Standalone executable build | `python build.py` (wraps PyInstaller with `build.spec`) |
| Test suite | `python -m pytest -q` (or `python -m unittest discover -s tests -v`, what CI runs) |
| Install the pinned FFmpeg into `bin/` | `python scripts/fetch_ffmpeg.py` (version + SHA256s in `ffmpeg.lock`) |
| Check an install or a built exe without the GUI | `python main.py --self-test` / `VideoEditor.exe --self-test` (`core/selftest.py`: FFmpeg, NVENC, decode setting, 25 required filters, a 1 s test export) |
| Open a project from the command line / a double-click | `python main.py path\to\project.vproj` (the installer registers `.vproj`) |
| Per-user installer | `installer/VideoEditor.iss` (compiled by `python build.py --installer`) |
| Single source of the version | `core.__version__` (currently `0.2.0`; `scripts/version_info.py` generates the exe version resource and checks release tags) |

There is a single UI entry point — unlike some Qt/Streamlit projects that accumulate several parallel front ends over time, this app has never had more than one `MainWindow`. `main.py` additionally shows a splash screen (if `assets/icons/splash.png` exists), sets the Windows taskbar `AppUserModelID` so the app doesn't get grouped under a generic Python icon, and warns (non-fatally) if FFmpeg can't be found on startup.

## Release

```text
dist/VideoEditor/VideoEditor.exe                -- PyInstaller onedir build (+ _internal/)
dist/installer/VideoEditor-<version>-setup.exe   -- per-user Inno Setup installer (Windows, --installer)
```

Build with `python build.py` (add `--installer` for the installer; uses `build.spec` and `installer/VideoEditor.iss`; see [packaging/workflow.md](workflows/packaging/workflow.md)). PyInstaller does not cross-compile — build on the OS you're targeting. Bundling `ffmpeg.exe`/`ffprobe.exe` in a `bin/` folder next to `build.spec` before building is optional but recommended so end users don't need FFmpeg on `PATH`. Generated `build/` and `dist/` folders are build artifacts, not source — safe to delete and regenerate.

`.github/workflows/release.yml` automates all of this: push a version tag (`git tag v0.1.0 && git push origin v0.1.0`) and it builds the app folder and its installer on a `windows-latest` runner (with the FFmpeg essentials build bundled), self-tests the exe, then publishes the installer and a portable zip of the folder as GitHub Release assets — unlike a workflow-run artifact, it doesn't expire after 90 days. **This repository is currently private**, so a release asset still requires a GitHub account with access to the repo to download (confirmed live: an unauthenticated request for the asset URL returns a plain `404`, not the file) — "publicly downloadable, no login" only becomes true if the repo's visibility is changed to public, which is a separate, deliberate decision (it exposes the full source/history too, not just the release), not something this workflow does on its own. Manually dispatching the workflow instead of pushing a tag builds from whatever's currently on the branch and publishes it as a `build-<short-sha>` prerelease, for a one-off/test build without cutting a real version. The test suite must pass in the same workflow run before the Windows build starts — a release is never published from a red build.

Builds use the Python in `.python-version` (3.14; `build.py` refuses another interpreter unless `--any-python`), installed from `requirements.txt` + `requirements-build.txt` with `requirements-lock.txt` (a clean-venv freeze by `scripts/make_lock.py`) as constraints, in CI and releases alike. `python build.py --installer --sign` Authenticode-signs `VideoEditor.exe`, the installer and its uninstaller (Inno Setup's SignTool) with the certificate whose SHA-1 thumbprint is in `VIDEO_EDITOR_SIGN_THUMBPRINT` or `CODESIGN_THUMBPRINT`, timestamped (DigiCert by default); the same wiring was checked with a self-signed test certificate on 2026-10-07 in the photo and media-player projects, not yet in a real build of this one.

## Known Limitations

- **Not yet done from the roadmap** (see `../improvement_reports/video_editor.md`, outside this repository): HDR passthrough needs every HDR source to share one transfer (mixed PQ+HLG timelines export as SDR or 10-bit SDR); HDR10 mastering metadata (mastering display, MaxCLL) is written only by the CPU HEVC encoder (x265) -- NVENC and AV1 exports carry the BT.2020/PQ/HLG tags only, because the filter graph doesn't pass frame side data to them; colour tools (eq, LUTs, keys) work on the HDR signal itself in an HDR export; H.264 and VP9 stay 8-bit. Stabilization is vid.stab (no `deshake` fallback for an FFmpeg built without it -- the self-test then reports the filters missing). Only parameters FFmpeg evaluates per frame are animatable (colour correction, vignette); keys, LUTs, blur, sharpen, denoise and stabilization settings are constant per clip. The timeline's accessibility tree was verified through Qt's own interfaces, not with a running screen reader (NVDA/Narrator); OS text scaling is still not honoured. FFmpeg is still the static build (no shared-library FFmpeg). The onedir build, the `.vproj` argument and a silent install/uninstall of the compiled installer are verified; an interactive install (Start menu entry, double-clicking a `.vproj`) and the release workflow's new folder/installer path have not been exercised yet.
- **Playback itself is verified manually.** The offscreen Qt tests cover panel and timeline logic, but `QMediaPlayer` output, drag interactions and the look of the timeline can't be checked headlessly.
- **A trimmed export starting inside a speed-ramped clip or a crossfade pair decodes that clip/pair from its start** (their inputs are trimmed after their chain rather than seeked). Every other clip is seeked, and clips outside the window aren't in the graph at all.
- **Reverse buffers the whole clip in memory** (FFmpeg's `reverse`/`areverse`), so long reversed clips need a lot of RAM at export; the preview steps through reversed clips and freeze frames silently (the export has the reversed sound). A split inside a freeze frame is refused. Subtitles are text clips: the export burns them in, muxes them as a soft stream (mov_text/srt/webvtt) or writes a sidecar `.srt`, but ASS/SSA styling is not kept (text and timing only; no libass rendering). The level meters read the import-time waveform of the clip under the playhead, not the live mix; the LUFS meter (Export dialog > Measure) measures the whole export range on demand, not live during playback. GPU decoding is opt-in (Playback > GPU Decoding, or `VIDEO_EDITOR_HWACCEL`, which wins) and measured slower than the CPU on this machine for synthetic 4K HEVC; there is no GPU-resident filter graph.
- **Playback is intentionally not WYSIWYG** for multi-track composites, transitions, and text; the **Accurate frame** option shows the exact export frame only while paused or scrubbing — see [preview-playback/workflow.md](workflows/preview-playback/workflow.md).
- **Ripple editing is same-track only** — Delete/Trim with Ripple on shift later clips on that same track, never other tracks. A plain drag never ripples; Shift+drag (Ripple Move) moves the clip and every later clip on its track, plus their linked clips -- other tracks stay put. Insert is the one edit that ripples every unlocked track. See [timeline-editing/workflow.md](workflows/timeline-editing/workflow.md).
- **Speed ramps are step segments, not a smooth continuous ramp**, and don't combine with Transform's scale/rotation or crossfade transitions. See [speed-ramps/workflow.md](workflows/speed-ramps/workflow.md) for why.
- **Fill-mode reframing has no automatic subject detection.** The crop focus point (for cropping a differently-shaped source into a vertical Shorts/TikTok/Reels canvas) is set manually per clip — there's no frame-content analysis to auto-track a subject. See [shorts-export/workflow.md](workflows/shorts-export/workflow.md).
- **The Shorts export preset is scoped to the user's own or properly licensed material.** It deliberately does not, and will not, include any feature aimed at republishing or monetizing someone else's copyrighted movie/series footage, or at evading platform copyright-detection systems (e.g. YouTube's Content ID) — no export setting or editing technique makes that non-infringing, monetized or not. This was an explicit scope decision, not an oversight.

- **GPU-accelerated export (NVENC), with automatic CPU fallback.** Single-pass exports to MP4/MOV/MKV/AVI/FLV (libx264's containers) can now encode with NVIDIA NVENC (`h264_nvenc`) instead of the CPU. `core/ffmpeg_utils.py::nvenc_available()` probes `ffmpeg -hide_banner -encoders` once (`lru_cache`'d for the process) rather than assuming it's there — the end user might lack an NVIDIA GPU, have an old driver, or be pointed at a system `ffmpeg` build without NVENC; it never raises, always resolving to "not available" on any failure. `ExportSettings.use_gpu` (default `True`) is read only by `Exporter._export_single_pass()` via the new `Exporter._resolve_video_codec()`/`NVENC_CODEC_MAP` — VP9 (`.webm`) has no NVENC entry, so it always stays on the CPU codec regardless of the setting. NVENC doesn't understand `-crf`; `Exporter._video_quality_args()` maps the existing CRF preset number onto NVENC's own `-preset p4 -rc:v vbr -cq:v <value> -b:v 0` instead of passing `-crf` to an encoder that would reject it (NVENC's `-cq` uses the same 0-51 lower-is-better scale as x264's `-crf`, so the existing 18/23/28 preset values carry over directly). If the GPU encode actually fails at runtime (driver issue, another process holding the GPU's limited concurrent NVENC session count, etc.), `_export_single_pass()` transparently retries once with the CPU codec and reports the fallback via the same `on_progress` status-message mechanism the rest of the export flow already uses, rather than failing the export outright — a CPU-side failure on the retry still raises normally. Two-pass, target-file-size exports always use the CPU codec regardless of `use_gpu`: NVENC's rate control doesn't use libx264's `-pass 1`/`-pass 2` log-file scheme, so mixing them wasn't worth the risk for a feature not requested here. `ui/export_dialog.py` gained a "Use GPU encoding (NVENC) when available" checkbox (checked and enabled by default only when `nvenc_available()` detects it), disabled with an explanatory tooltip for `.webm`/GIF output or while Two-pass is checked, matching what the exporter itself will actually do. Verified via mocked-`subprocess.Popen` tests only (`tests/test_ffmpeg_utils.py`, `tests/test_exporter.py::GpuExportIntegrationTests`) — no test depends on this machine's actual GPU; the "NVENC fails mid-render, falls back to CPU" path is exercised with a fake process that fails only when `h264_nvenc` is in its argument list.

HDR (PQ/HLG) is tone-mapped with `zscale`+`tonemap`, SD is converted to the BT.709 matrix, and outputs are tagged BT.709 with `setparams` (the `-color_*` output options alone were ignored by this FFmpeg). A generic effect stack (`core/effects.py`: LUT, YUV chroma key + despill, sharpen, blur, vignette, video denoise). HEVC/AV1/ProRes/DNxHR, tuned NVENC flags (measured 1.03-1.24x the time of plain p4), per-encoder NVENC probes, GPU target size. Default subprocess timeouts; export-time probe failures become warnings. Shared chain and output-argument builders; `transition_in`, `track_index` and an unused signal removed.

Verified on a real build (2026-10-01): 117.4 MB one-file exe (was 163.5 MB) unpacking 293 MB per launch (was 435.5 MB), `VideoEditor.exe --self-test` passes against the bundled FFmpeg, the app launches to its main window in about 3.5-3.8 s, and the exe's version resource reads 0.2.0.0 from `core.__version__`.

- **Batch of export/editing bugs found in review (Sept 2026).** Each has regression tests; the FFmpeg-dependent ones run against `bin/ffmpeg.exe` (or `ffmpeg` on `PATH`) and skip when neither exists, so the suite still needs no FFmpeg:
  - **Non-ASCII file names** (`Árbol.mp4`) imported as broken zero-length assets and could crash export: `core/ffmpeg_utils.run()`/`popen()` decoded FFmpeg's UTF-8 output with the Windows code page. Now `encoding="utf-8", errors="replace"`. `probe_file()` also raises `MediaProbeError` (shown as a per-file import error) when ffprobe fails or finds no audio/video stream, instead of returning an empty asset.
  - **Text overlays containing `'` or `%` broke export.** Text now goes through `drawtext=textfile=` (a temp UTF-8 file, path escaped for both filtergraph parsing levels) with `expansion=none`; `GraphResult.temp_files`/`cleanup()` hold the files for the whole export. Verified with real FFmpeg on "Don't stop", "50% at 10:30", `%{pts}`, multi-line text, and a temp folder named `o'brien tmp,[x];y`.
  - **Split** gave the new half the id `<id>_b` (duplicate ids on repeated splits) and copied all keyframes into both halves. Now: a fresh uuid (stable across redo), opacity/position keyframes cut at the split and re-based (with an interpolated keyframe at the cut), and speed ramps split at the source frame actually on screen (`Clip.speed_segments`), with each half's speed keyframes re-based too.
  - **Track Hide/Mute:** hidden now removes the picture but keeps the audio; muted now silences a video track's embedded audio in export, and the preview honors track mute. The header's mute/lock/hide (and duck-trigger) toggles go through `UpdateTrackPropertyCommand`, so they're undoable.
  - **Export errors** now carry the last 30 FFmpeg log lines (`ExportError.log_tail`) instead of just "exited with code N", and export fails up front listing any missing source files.
  - **Exports render to `name.partial.ext`** in the destination folder and `os.replace` onto the real name only on success. A failed or cancelled export no longer leaves a truncated file or overwrites a good previous export.
  - **NVENC detection** now does a real cached test encode (`nullsrc` 0.1 s into `h264_nvenc`), not just an encoder-list check. The main window warms it on a background thread. The CPU fallback now re-renders only when the failure looks GPU-specific (NVENC/CUDA/driver text in the log, or failure before any output), not after any error.
  - **`adelay`** delayed only the first two channels (`<ms>|<ms>`). It's now `adelay=delays=<ms>:all=1`.
  - **Project saves and autosaves are atomic** (`core.project.write_json_atomic`: temp file + fsync + `os.replace`), and the unsaved-changes prompt is now Save / Discard / Cancel.
  - **Crossfade A/V desync.** The second clip's audio lagged its picture by the transition duration. See [color-and-effects](workflows/color-and-effects/workflow.md).
- **Two-pass export was completely broken, for every project, regardless of markers: "... has output ... unconnected."** Found while verifying that chapter embedding (above) didn't interfere with two-pass export — it turned out two-pass itself had never actually been run end-to-end against real FFmpeg before. Pass 1 (`-an`, video-only, output discarded) never mapped or otherwise consumed the base filter graph's always-present audio output pad (`[aout]`, even a silent `anullsrc` one when nothing is audible), and FFmpeg refuses to run at all with an unconsumed named filtergraph output — the identical class of bug GIF export hit earlier in this same file. **Fixed** the same way: pass 1 now routes `[aout]` into an `anullsink`. Verified against real FFmpeg for both the no-audio and has-audio cases, plus a new mocked-`subprocess.Popen` regression test (`tests/test_exporter.py`, a deliberate narrow exception to "no unit tests for `core/exporter.py`" — see that file's own docstring) that asserts pass 1's filter graph contains `anullsink`, so this can't silently regress again.
- **Speed-ramped clip export crashed when combined with a fade or volume/delay adjustment: "No such filter: ''".** `_maybe_add_speed_ramped_audio()`'s trailing fade/volume/timeline-delay suffix was appended straight after a bracket reference (`"[label]" + ",afade=..."`, i.e. `"[label],afade=..."`) — a comma immediately after a `[label]` reference is invalid FFmpeg filtergraph syntax (parsed as an empty filter name) and aborts the whole export. The equivalent video-side code (`_video_fade_and_opacity_suffix`'s caller) already stripped this leading comma correctly; the audio counterpart was simply missed. **Fixed** by stripping it there too, plus a regression test asserting the generated graph never contains `"],afade"`/`"],fade"`. Caught only by real FFmpeg execution (a speed-ramped clip with `fade_in`/`fade_out` set) — the text-based filter-graph tests for speed ramps existed already but hadn't happened to combine a ramp with a fade.
- **Crossfade export crashed against real FFmpeg: "xfade" requires constant-frame-rate inputs.** Caught only by actually running a crossfade export through real FFmpeg (the text-based filter-graph unit tests can't catch this class of bug, since they never execute FFmpeg) — `"[Parsed_xfade] The inputs needs to be a constant frame rate; current rate of 1/0 is invalid"` aborted the whole export. Neither `setpts=PTS-STARTPTS` nor the exporter's final `-r` flag actually guarantees constant frame rate on the two streams feeding into `xfade` specifically (`overlay`, used for every other clip, has no such requirement, which is why this didn't surface until crossfade was exercised end-to-end). **Fixed**: both sides of a crossfade pair now get an explicit `fps={fps}` filter appended right before merging. Verified against real FFmpeg (a synthetic red/blue crossfade, sampling pixel color before/during/after the transition) with a regression test asserting the `fps=` filter is present exactly twice per pair.
- **GIF export crashed with "output unconnected."** `build_filter_graph()` always produces an audio pad (`[aout]`, even a silent `anullsrc` one when nothing is audible — see the export workflow doc). GIF has no audio, so `_export_gif()` correctly never mapped it — but FFmpeg refuses to run at all if a named filtergraph output is left unconsumed by anything. **Fixed**: routes `[aout]` into an `anullsink` (FFmpeg's filter designed exactly for "discard this output cleanly") alongside the palette-based video chain. Also caught only by real FFmpeg execution, not the text-based filter-graph tests.
- **An audio-only clip's Fade In/Out sliders did nothing.** The Properties panel shows Fade In/Out for every non-text clip, including audio, and the values were saved to the project — but `core/filter_graph.py::_build_audio_chain()` never applied them; only a video clip's alpha channel got `fade=...:alpha=1`. **Fixed**: `_build_audio_chain()` now applies the matching `afade=t=in:...`/`afade=t=out:...` filters, so fades work for standalone audio clips and also duck a video clip's own embedded audio during its fade.
- **Track headers visually overlapped the first ~3 seconds of every track's clips and scrolled away with the timeline instead of staying pinned.** `ui/widgets/timeline_items.py`'s `TrackHeaderItem` (the sticky name/mute/lock/hide panel, `HEADER_WIDTH = 130`) lived at the same scene x-origin as `ClipItem`s and the ruler, with a higher z-value — so it sat on top of, rather than beside, the start of the timeline, and scrolling right made it disappear along with the content, losing track identity entirely. **Fixed**: clip items, the ruler, the playhead, and the snap guide now all start at scene x = `HEADER_WIDTH`; the header column and a new `CornerItem` (covering the top-left corner above the ruler) stay pinned to the viewport's left edge via `TimelineWidget._pin_header_items()`, connected to the view's horizontal scrollbar `valueChanged` signal and re-applied after every `rebuild()`. A headless smoke test (`QT_QPA_PLATFORM=offscreen`) exercising zoom + scroll + rebuild caught and fixed a follow-on crash from this change: `scene.setSceneRect()` can synchronously fire a scrollbar `valueChanged` mid-`rebuild()`, momentarily pointing `_pin_header_items()` at an already-deleted `CornerItem` from the just-cleared scene — fixed by creating the corner item before `setSceneRect()` runs, plus a defensive `try/except RuntimeError` around the pin loop.
- **Export could fail outright for a clip whose source file wasn't in the project's media pool.** `core/filter_graph.py` decided whether to map a clip's `[N:a]` audio stream by checking `project.find_asset_by_path()`, defaulting to `has_audio=True` when no matching pool entry existed (e.g. the asset had been removed from the pool, or the project file was hand-edited). If the clip's source genuinely had no audio track, FFmpeg would fail the entire `-filter_complex` graph trying to map a non-existent stream. **Fixed**: `_clip_has_audio()` now falls back to probing the file directly (`core.media_probe.probe_file`) when no pool asset matches, defaulting to `False` (silent, not a crash) if even that fails.
- **The "two-pass" export setting was inert.** `ExportSettings.two_pass` existed as a dataclass field but was never read anywhere in `Exporter.export()`, and the export dialog didn't even expose a control for it. **Fixed**: implemented real two-pass, target-file-size encoding — `Exporter._export_two_pass()` computes a video bitrate budget from a target size in MB and the project duration, then runs an FFmpeg analysis pass (video only, discarded output) followed by the real encode pass at that bitrate. `ui/export_dialog.py` gained a "Two-pass, target file size" checkbox and an MB field.
- **Importing media froze the UI.** `MainWindow.import_media_paths()` ran `probe_file()`/`generate_thumbnail()`/`generate_waveform()` synchronously in a loop on the UI thread, papering over the freeze with `QCoreApplication.processEvents()` — a batch of large files would visibly hang the app. **Fixed**: the work now runs in `ui/import_worker.py::ImportWorker` on its own `QThread` (the same pattern the export dialog already used), with a status-bar progress bar; the main thread only handles the final `Project`/UI updates via signal handlers.
- **No feedback for missing media.** Importing a path that no longer exists, or opening a `.vproj` referencing moved/deleted files, failed silently. **Fixed**: `ImportWorker` now checks `os.path.isfile()` before probing and reports a clear per-file error instead of mis-probing a nonexistent path; `MainWindow.open_project()` now warns (listing up to 10 paths) if any media in the loaded project's pool can't be found on disk.
- **Closing the export dialog while FFmpeg was still running could destroy a live `QThread`.** `ExportDialog.closeEvent()` cancelled and waited only 3 seconds for the render thread before closing regardless of whether FFmpeg had actually exited. **Fixed**: `Exporter.cancel()` now terminates the FFmpeg subprocess immediately (stored as `self._process`) instead of waiting for the run loop to next notice a cancellation flag between progress lines; `closeEvent()` now refuses to close (with a message asking the user to wait) if the thread still hasn't stopped after 5 seconds, rather than destroying it mid-flight.
- **No overwrite confirmation on export.** Picking an existing output filename silently replaced it. **Fixed**: `ExportDialog._on_export()` now asks for confirmation first.
- **No crash recovery.** A crash mid-edit lost all unsaved work, with no autosave of any kind. **Fixed**: `MainWindow` now autosaves the current project to a dedicated recovery slot (`~/.video_editor/autosave/autosave.vproj`, separate from the user's actual project file) every 2 minutes while dirty, and offers to restore it on the next launch if found; the slot is cleared on a successful save or a confirmed discard, so it never resurrects work the user explicitly saved or threw away.
