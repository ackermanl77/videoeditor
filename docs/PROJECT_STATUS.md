# Project Status

## Architecture

```text
main.py (PySide6 QApplication entry point)
        |
        v
ui/  (MainWindow, TimelineWidget, PreviewPlayer, PropertiesPanel, MediaBinWidget, ExportDialog)
        |  reads Project/Track/Clip directly, but every mutation goes
        |  through a Command object executed via core.history.History
        v
core/ (Project, Track, Clip, History/Commands, FilterGraph, Exporter, MediaProbe, Waveform)
        |
        v
FFmpeg / FFprobe (subprocess, via core/ffmpeg_utils.py)
```

`core/` is the entire editing model and the FFmpeg render pipeline, with **zero Qt/GUI dependencies** — every module under `core/` can be imported and unit-tested (see `tests/`) without a display, and the whole test suite runs in well under a second. `ui/` only *reads* from `core` and issues `Command` objects (`core/commands.py`) through `core.history.History`, so every editing operation (add/move/trim/split/delete a clip, add/remove a track, change any clip property) is undoable by construction; the UI never mutates `Project`/`Track`/`Clip` directly outside of a `Command`.

The preview (`ui/preview_player.py`) and the export pipeline (`core/filter_graph.py` + `core/exporter.py`) are two independent renderers of the same `Project`, and they deliberately don't agree on everything: the preview plays only the topmost active video clip through `QMediaPlayer` (no real-time multi-track alpha compositing), while export always builds a full `-filter_complex` graph and renders the true composited timeline — transitions, opacity, fades, and text overlays included. This is a conscious simplicity/fidelity trade-off, not a bug; see [preview-playback/workflow.md](workflows/preview-playback/workflow.md).

`core/ffmpeg_utils.py` centralizes how `ffmpeg`/`ffprobe` are located (bundled next to a PyInstaller build, then system `PATH`, then the `imageio-ffmpeg` package as a last resort) so no other module has to know how the binary was found.

## Primary Entry Points

| Purpose | Entry point |
|---|---|
| Desktop application | `python main.py` |
| Standalone executable build | `python build.py` (wraps PyInstaller with `build.spec`) |
| Unit test suite (no Qt/display required) | `python -m unittest discover -s tests -v` |

There is a single UI entry point — unlike some Qt/Streamlit projects that accumulate several parallel front ends over time, this app has never had more than one `MainWindow`. `main.py` additionally shows a splash screen (if `assets/icons/splash.png` exists), sets the Windows taskbar `AppUserModelID` so the app doesn't get grouped under a generic Python icon, and warns (non-fatally) if FFmpeg can't be found on startup.

## Release

```text
dist/VideoEditor.exe        -- PyInstaller one-file build (Windows)
dist/VideoEditor             -- same, no extension (macOS/Linux)
```

Build with `python build.py` (uses `build.spec`; see [packaging/workflow.md](workflows/packaging/workflow.md)). PyInstaller does not cross-compile — build on the OS you're targeting. Bundling `ffmpeg.exe`/`ffprobe.exe` in a `bin/` folder next to `build.spec` before building is optional but recommended so end users don't need FFmpeg on `PATH`. Generated `build/` and `dist/` folders are build artifacts, not source — safe to delete and regenerate.

`.github/workflows/release.yml` automates all of this: push a version tag (`git tag v0.1.0 && git push origin v0.1.0`) and it builds `VideoEditor.exe` on a `windows-latest` runner (with the FFmpeg essentials build bundled), then publishes it as a GitHub Release asset — unlike a workflow-run artifact, it doesn't expire after 90 days. **This repository is currently private**, so a release asset still requires a GitHub account with access to the repo to download (confirmed live: an unauthenticated request for the asset URL returns a plain `404`, not the file) — "publicly downloadable, no login" only becomes true if the repo's visibility is changed to public, which is a separate, deliberate decision (it exposes the full source/history too, not just the release), not something this workflow does on its own. Manually dispatching the workflow instead of pushing a tag builds from whatever's currently on the branch and publishes it as a `build-<short-sha>` prerelease, for a one-off/test build without cutting a real version. The test suite must pass in the same workflow run before the Windows build starts — a release is never published from a red build.

## Verification

```powershell
python -m unittest discover -s tests -v
```

91 tests as of this writing, covering `core/` only (`clip`/`track` duration and overlap math, command undo/redo, filter-graph text construction and escaping, project serialization round-trips, and waveform peak extraction). None of them require FFmpeg to be installed or a display to be present — they test the graph-building *text*, not actual FFmpeg execution. There is no automated UI test coverage (no Qt widget tests); UI changes are currently verified manually (headless smoke construction + interaction scripts under `QT_QPA_PLATFORM=offscreen`, not checked into the repo as a suite).

GitHub Actions (`.github/workflows/ci.yml`) runs the same command on every push and pull request — with no `pip install` step at all. `core/` (everything `tests/` exercises) has zero third-party imports (confirmed by grepping every `core/*.py` import line — only stdlib: `dataclasses`, `json`, `os`, `subprocess`, `tempfile`, etc.); the three packages in `requirements.txt` (PySide6 for the UI, `imageio-ffmpeg` as a fallback FFmpeg binary, `pyinstaller` for packaging) are never imported by anything under `tests/`. Running CI with nothing installed is a continuous, enforced check of that architectural boundary, not just an optimization — if a future change makes `core/` (or a test) depend on a third-party package, `unittest discover`'s own import step fails immediately, the same as any other missing dependency would. Verified locally against a bare venv with an empty `site-packages` before adding the workflow: `python -m compileall -q core ui main.py` and the full test suite both pass with zero packages installed.

## Known Limitations

- **No automated UI tests.** `tests/` covers `core/` exhaustively but nothing under `ui/` — a regression in `TimelineWidget`, `PreviewPlayer`, or the dialogs would only surface manually or in production.
- **No project-level relink UI for offline media.** Opening a project whose source files have moved warns the user (see [project-files/workflow.md](workflows/project-files/workflow.md)) but there's no in-app way to point a clip at a new path; the file has to be restored at its original location.
- **Preview is intentionally not WYSIWYG** for multi-track composites, transitions, and text — see [preview-playback/workflow.md](workflows/preview-playback/workflow.md). This is a documented design trade-off, not a defect.
- **Ripple editing is same-track only** — Delete/Trim with Ripple on shift later clips on that same track, never other tracks. Plain Move (dragging) is never rippled, only Delete/Trim. See [timeline-editing/workflow.md](workflows/timeline-editing/workflow.md).
- **Speed ramps are step segments, not a smooth continuous ramp**, and don't combine with Transform's scale/rotation or crossfade transitions. See [speed-ramps/workflow.md](workflows/speed-ramps/workflow.md) for why.
- **Fill-mode reframing has no automatic subject detection.** The crop focus point (for cropping a differently-shaped source into a vertical Shorts/TikTok/Reels canvas) is set manually per clip — there's no frame-content analysis to auto-track a subject. See [shorts-export/workflow.md](workflows/shorts-export/workflow.md).
- **The Shorts export preset is scoped to the user's own or properly licensed material.** It deliberately does not, and will not, include any feature aimed at republishing or monetizing someone else's copyrighted movie/series footage, or at evading platform copyright-detection systems (e.g. YouTube's Content ID) — no export setting or editing technique makes that non-infringing, monetized or not. This was an explicit scope decision, not an oversight.

## Recently Added

- **Collapsible Properties-panel groups.** Found via a live, headless UI audit that measured (not guessed) the problem: selecting a video/image clip renders 7 stacked group boxes (Clip Adjustments through Chroma Key) needing ~1,376px of vertical space, against a panel whose actual allotted height on a typical window is only ~500-540px (`main_splitter`'s 3:2 stretch ratio against the timeline below it) — roughly 2.5-3x more scrolling than the visible area, with the Keyframes group alone (all three keyframe tables always rendered, even empty) accounting for 522px of that. **Fixed**: new `CollapsibleGroupBox` (`ui/properties_panel.py`) — a `QGroupBox` subclass where unchecking the (visible, always-clickable) checkbox actually `setVisible(False)`s every one of the group's own widgets, not just disables them the way plain `QGroupBox.setCheckable()` does (which leaves them full-size and still visible, solving nothing); a "▼"/"▶" prefix on the title makes the click target's purpose ("show/hide this section," not "enable/disable a feature") unambiguous. Clip Adjustments, Transform, and Color Correction default expanded; Reframe, Keyframes, Transition, and Chroma Key default collapsed. Measured, not estimated: the same headless audit re-run against the real defaults showed the content dropping to 426x717 — a real ~48% height reduction. **A real bug caught during that verification**, not shipped and then found later: the initial collapse state was applied in the constructor before `_build_ui()` had added the group's own rows yet, so nothing was actually hidden at startup — fixed by re-syncing every group's visibility once at the true end of `_build_ui()`. See [clip-properties/workflow.md](workflows/clip-properties/workflow.md).
- **Automated release builds (GitHub Actions).** `.github/workflows/release.yml` builds `VideoEditor.exe` on a `windows-latest` runner (PyInstaller can't cross-compile) with the FFmpeg essentials build bundled, and publishes it as a GitHub Release asset — triggered by pushing a version tag, or manually via `workflow_dispatch` for a `build-<short-sha>` prerelease. A dedicated `test` job (duplicating `ci.yml`'s own test step, since `ci.yml` doesn't trigger on a tag push) gates the Windows build — nothing is ever published without the suite passing first. Every action is pinned to a commit SHA, matching `ci.yml`'s own convention. See "Release" above.
- **Continuous integration (GitHub Actions).** `.github/workflows/ci.yml` runs the compile check and the full test suite on every push and pull request against `main`/`master`, plus manual `workflow_dispatch` — parity with the sibling `photo_professional_tool` project's own CI setup. Deliberately simpler than that project's workflow: no `pip install` step at all, since `core/` (everything `tests/` touches) has zero third-party dependencies. New CI badge at the top of `README.md`. See "Verification" above for how this was confirmed against a bare, package-free venv before being added.
- **Shorts / vertical video export preset.** Auto-crop to a vertical 9:16 canvas instead of letterboxing, a duration cap, and ready-made platform presets — for the user's own or properly licensed footage (see Known Limitations above for the explicit scope decision behind this). New per-clip `Clip.reframe_mode` (`FIT`/`FILL`) + `crop_focus_x`/`crop_focus_y`: `FILL` scales to *cover* the canvas and crops the overflow centered on the focus point, instead of `FIT`'s scale-to-fit-and-letterbox — exposed as a **Fill Frame** checkbox + **Crop Focus X/Y** sliders in the Properties panel's new "Reframe (Vertical / Shorts)" group. `build_filter_graph()` gained `reframe_override` (forces every clip's reframe mode for one export only, without touching the project's own stored per-clip settings — implemented via a deep-copy-and-override helper, used by the Export dialog's **Auto-fill vertical frame** checkbox) and `trim_range` (wraps the final composited video/audio in `trim`/`atrim`, used for the duration cap and threaded through to `ExportSettings.trim_start`/`trim_end`). The Export dialog gained a **Shorts Platform** preset combo (YouTube Shorts/TikTok/Instagram Reels) that applies a 1080x1920 resolution, 30fps, auto-fill, and each platform's typical duration cap in one click. Chapters correctly re-anchor to a trimmed output's own 0-based timeline (dropping any chapter entirely outside the trimmed range) rather than keeping their original untrimmed times. Verified against real FFmpeg end-to-end: the crop-to-fill technique's focus-point behavior, a full trimmed+chaptered+Fill-mode export producing the exact predicted resolution/duration/chapter timestamps, and the export-wide override producing the same result without mutating the source clip. See [shorts-export/workflow.md](workflows/shorts-export/workflow.md).
- **Markers and chapters.** New `Marker` model on `Project` (a named point on the shared timeline, independent of any clip/track) — add one at the playhead via the timeline toolbar's **+ Marker** button, `M`, or **Timeline > Add Marker at Playhead**; rendered as a small colored flag with a dashed line through the tracks, click to seek, right-click to Rename/Delete. Markers participate in timeline snapping alongside clip edges/the playhead/`0:00`. On export, every marker becomes a real, player-navigable chapter (all formats except GIF) via an FFmpeg FFMETADATA pseudo-input (`-f ffmetadata -i ... -map_metadata N`) — a metadata-only input with no A/V streams of its own, so it doesn't disturb any `[N:v]`/`[N:a]` index the filter graph already references. New `AddMarkerCommand`/`RemoveMarkerCommand`/`RenameMarkerCommand`, all undoable. See [markers-and-chapters/workflow.md](workflows/markers-and-chapters/workflow.md). **This surfaced a real, previously-undetected bug** — see "Recently Fixed" below.
- **Basic keyframing for Opacity and Position.** Both can now animate smoothly over time instead of holding one constant value — set the slider, add a keyframe at a given clip-local time, repeat; 2+ keyframes override the plain slider with piecewise-linear interpolation. Position reuses Transform's `overlay=x:y` mechanism with a time-varying expression; Opacity uses a `geq` alpha ramp instead of `colorchannelmixer` (whose options aren't per-frame expressions in this FFmpeg build). New "Keyframes" group in the Properties panel (a small table + Add/Remove, not an on-timeline curve editor — a deliberately scoped "basic" MVP). Verified against real FFmpeg: both a `geq` alpha ramp and an `overlay` position ramp were sampled at multiple timestamps and matched the predicted linear-interpolation math almost exactly. **Known limit**: like Transform, position keyframes are a no-op on a crossfading clip. See [color-and-effects/workflow.md](workflows/color-and-effects/workflow.md).
- **Ripple delete/trim mode.** A new "Ripple" toggle in the timeline toolbar: with it on, Delete and Trim (either edge) also shift every later clip on the *same track* to close or open the resulting gap, instead of always leaving one (the prior overwrite-only behavior). Same-track only, by design (see the workflow doc for why). New `core.history.CompositeCommand` bundles the primary Remove/Trim with a `MoveClipCommand` per shifted clip into one atomic undo step. See [timeline-editing/workflow.md](workflows/timeline-editing/workflow.md).
- **Speed ramps (variable speed within a clip).** A clip's Speed can now vary over its own duration via 2+ speed keyframes, instead of one constant value for the whole clip — e.g. normal, then slow-motion, then normal again. Implemented as discrete constant-speed *segments* (a step change at each keyframe), each its own `trim`+`setpts`, concatenated with FFmpeg's `concat` filter — a deliberate, safer alternative to a mathematically continuous `setpts` ramp (see the workflow doc for the full reasoning). This surfaced a real, and important, correctness fix: `Clip.duration` previously only knew about the constant `speed` field, so a speed-ramped clip's *actual* rendered length would have silently diverged from what the timeline/overlap-checking/UI thought it was — `Clip.duration`/`Track.has_overlap()` etc. now all correctly reflect ramped timing via a new `Clip.speed_segments` property, computed once and shared by both the UI-facing timing model and the export filter graph. **Known limits**: doesn't combine with Transform's scale/rotation or crossfade transitions (both documented no-ops, `concat` requires matching segment sizes / a single continuous chain respectively); a standalone AUDIO-track clip's own speed ramp isn't implemented yet (only a video/image clip's *embedded* audio gets the segmented treatment). See [speed-ramps/workflow.md](workflows/speed-ramps/workflow.md).
- **Per-clip Transform (position, scale, rotation).** Previously every video/image clip was unconditionally scaled-to-fit and centered on the canvas via a fixed `pad` step — no way to do picture-in-picture, split-screen, or off-center framing, the single biggest feature gap versus comparable open-source editors (OpenShot, Kdenlive, Shotcut all treat this as core). Added `Clip.transform_x`/`transform_y`/`transform_scale`/`transform_rotation` with sliders in the Properties panel's new "Transform" group (video/image clips only). Implementation replaced the old unconditional `pad`-to-canvas step with FFmpeg's `overlay=x:y` using an expression that positions the clip's (optionally scaled/rotated) frame by its center — at the defaults this evaluates to exactly the same result `pad` used to produce, so an unedited clip's export is pixel-identical to before. A real side-effect fix, not just a new feature: a mismatched-aspect-ratio clip on a track *above* another video track used to block the layer beneath it with opaque black letterbox bars (baked into the old `pad` step); it now correctly lets the lower track show through, since there's no padding to begin with. Verified against real FFmpeg execution, not just the text-based filter-graph tests — including a genuine picture-in-picture composite confirming the background is visible everywhere the smaller, repositioned foreground clip doesn't cover. **Known limit**: Transform is a documented no-op on a clip while it's crossfading into the next one (`xfade` requires both its inputs to be the same frame size, which Transform's variable-size overlay approach can't guarantee for two different clips at once) — see [color-and-effects/workflow.md](workflows/color-and-effects/workflow.md).
- **Crossfade transitions between adjacent clips.** `Clip.transition_out`/`TransitionType` existed in the data model and round-tripped through `.vproj` files, but nothing ever read them — no UI control, and the export filter graph ignored them entirely. Setting a clip's transition to Crossfade (Properties panel, video/image clips only) now blends its tail into the next clip on the same track over `Clip.transition_duration` seconds, via `core/filter_graph.py::_find_crossfade_partner()` + FFmpeg's `xfade` filter, whenever that next clip immediately follows with no gap (clips can't overlap per `Track.has_overlap()`). Scope, deliberately: only one crossfade pair per boundary (chaining three or more consecutive crossfades isn't supported), video only (each side's audio stays independent, meeting at a clean cut rather than an `acrossfade`), and the pair's combined on-screen footprint is `transition_duration` seconds shorter than the sum of both clips' durations — nothing downstream on that track is auto-shifted to close the resulting gap, so there is a `transition_duration`-second gap on that track after a crossfaded pair unless the next clip is manually nudged left. See [color-and-effects/workflow.md](workflows/color-and-effects/workflow.md).
- **Per-clip color correction.** Video/image clips gained `brightness`/`contrast`/`saturation`/`gamma` fields (neutral defaults matching FFmpeg's `eq` filter, so an unedited clip never emits it) with sliders in the Properties panel's new "Color Correction" group.
- **Chroma key (green screen).** Video/image clips gained `chroma_key_enabled`/`chroma_key_color`/`chroma_key_similarity`/`chroma_key_blend`, applied via FFmpeg's `colorkey` filter right after the clip reaches `format=yuva420p` — the keyed-out pixels become transparent through the exact same alpha channel opacity/fades already use, so it composites with the existing `overlay` stack with no structural changes needed. Exposed in the Properties panel's new "Chroma Key" group.
- **Broader import format support.** `ui/media_bin.py::SUPPORTED_EXTENSIONS` only listed a handful of extensions per media kind, even though decoding itself is generic (any container/codec the installed FFmpeg build can decode already worked, just not offered by the file-picker's default filter or the drag-and-drop mental model). Added the common formats users actually run into: video (FLV, WMV, MPG/MPEG, 3GP, TS/MTS/M2TS, OGV, VOB), audio (Opus, WMA, AIFF), and images (GIF, `.tif`). `core/media_probe.py::IMAGE_EXTENSIONS` (previously duplicated inline in two places) is now a shared module-level constant so the "which extensions get treated as a still image rather than a 1-frame video" list can't drift out of sync with itself — it also gained `.tif` and `.gif` to match.
- **More export formats: AVI, FLV, and animated GIF.** Only MP4/MOV/MKV/WebM were offered. AVI and FLV reuse the existing libx264/aac pipeline (`CONTAINER_CODECS`) — both are standard, well-supported combinations in those containers. GIF needed a real dedicated path (`Exporter._export_gif()`): no audio track, no CRF/bitrate concept, and FFmpeg's default per-frame GIF quantizer looks visibly banded, so it uses the standard two-stage `palettegen`/`paletteuse` (Bayer-dithered) workflow for a single clip-wide 256-color palette instead. The export dialog disables Quality/Two-pass and shows an explanatory note when GIF is selected, since neither applies.

## Recently Fixed

- **Two-pass export was completely broken, for every project, regardless of markers: "... has output ... unconnected."** Found while verifying that chapter embedding (above) didn't interfere with two-pass export — it turned out two-pass itself had never actually been run end-to-end against real FFmpeg before. Pass 1 (`-an`, video-only, output discarded) never mapped or otherwise consumed the base filter graph's always-present audio output pad (`[aout]`, even a silent `anullsrc` one when nothing is audible), and FFmpeg refuses to run at all with an unconsumed named filtergraph output — the identical class of bug GIF export hit earlier in this same file. **Fixed** the same way: pass 1 now routes `[aout]` into an `anullsink`. Verified against real FFmpeg for both the no-audio and has-audio cases, plus a new mocked-`subprocess.Popen` regression test (`tests/test_exporter.py`, a deliberate narrow exception to "no unit tests for `core/exporter.py`" — see that file's own docstring) that asserts pass 1's filter graph contains `anullsink`, so this can't silently regress again.
- **Speed-ramped clip export crashed when combined with a fade or volume/delay adjustment: "No such filter: ''".** `_maybe_add_speed_ramped_audio()`'s trailing fade/volume/timeline-delay suffix was appended straight after a bracket reference (`"[label]" + ",afade=..."`, i.e. `"[label],afade=..."`) — a comma immediately after a `[label]` reference is invalid FFmpeg filtergraph syntax (parsed as an empty filter name) and aborts the whole export. The equivalent video-side code (`_video_fade_and_opacity_suffix`'s caller) already stripped this leading comma correctly; the audio counterpart was simply missed. **Fixed** by stripping it there too, plus a regression test asserting the generated graph never contains `"],afade"`/`"],fade"`. Caught only by real FFmpeg execution (a speed-ramped clip with `fade_in`/`fade_out` set) — the text-based filter-graph tests for speed ramps existed already but hadn't happened to combine a ramp with a fade.
- **Crossfade export crashed against real FFmpeg: "xfade" requires constant-frame-rate inputs.** Caught only by actually running a crossfade export through real FFmpeg (the text-based filter-graph unit tests can't catch this class of bug, since they never execute FFmpeg) — `"[Parsed_xfade] The inputs needs to be a constant frame rate; current rate of 1/0 is invalid"` aborted the whole export. Neither `setpts=PTS-STARTPTS` nor the exporter's final `-r` flag actually guarantees constant frame rate on the two streams feeding into `xfade` specifically (`overlay`, used for every other clip, has no such requirement, which is why this didn't surface until crossfade was exercised end-to-end). **Fixed**: both sides of a crossfade pair now get an explicit `fps={fps}` filter appended right before merging. Verified against real FFmpeg (a synthetic red/blue crossfade, sampling pixel color before/during/after the transition) with a regression test asserting the `fps=` filter is present exactly twice per pair.
- **GIF export crashed with "output unconnected."** `build_filter_graph()` always produces an audio pad (`[aout]`, even a silent `anullsrc` one when nothing is audible — see the export workflow doc). GIF has no audio, so `_export_gif()` correctly never mapped it — but FFmpeg refuses to run at all if a named filtergraph output is left unconsumed by anything. **Fixed**: routes `[aout]` into an `anullsink` (FFmpeg's filter designed exactly for "discard this output cleanly") alongside the palette-based video chain. Also caught only by real FFmpeg execution, not the text-based filter-graph tests.
- **An audio-only clip's Fade In/Out sliders did nothing.** The Properties panel shows Fade In/Out for every non-text clip, including audio, and the values were saved to the project — but `core/filter_graph.py::_build_audio_chain()` never applied them; only a video clip's alpha channel got `fade=...:alpha=1`. **Fixed**: `_build_audio_chain()` now applies the matching `afade=t=in:...`/`afade=t=out:...` filters, so fades work for standalone audio clips and also duck a video clip's own embedded audio during its fade.
- **Track headers visually overlapped the first ~3 seconds of every track's clips and scrolled away with the timeline instead of staying pinned.** `ui/widgets/timeline_items.py`'s `TrackHeaderItem` (the sticky name/mute/lock/hide panel, `HEADER_WIDTH = 130`) lived at the same scene x-origin as `ClipItem`s and the ruler, with a higher z-value — so it sat on top of, rather than beside, the start of the timeline, and scrolling right made it disappear along with the content, losing track identity entirely. **Fixed**: clip items, the ruler, the playhead, and the snap guide now all start at scene x = `HEADER_WIDTH`; the header column and a new `CornerItem` (covering the top-left corner above the ruler) stay pinned to the viewport's left edge via `TimelineWidget._pin_header_items()`, connected to the view's horizontal scrollbar `valueChanged` signal and re-applied after every `rebuild()`. A headless smoke test (`QT_QPA_PLATFORM=offscreen`) exercising zoom + scroll + rebuild caught and fixed a follow-on crash from this change: `scene.setSceneRect()` can synchronously fire a scrollbar `valueChanged` mid-`rebuild()`, momentarily pointing `_pin_header_items()` at an already-deleted `CornerItem` from the just-cleared scene — fixed by creating the corner item before `setSceneRect()` runs, plus a defensive `try/except RuntimeError` around the pin loop.
- **Export could fail outright for a clip whose source file wasn't in the project's media pool.** `core/filter_graph.py` decided whether to map a clip's `[N:a]` audio stream by checking `project.find_asset_by_path()`, defaulting to `has_audio=True` when no matching pool entry existed (e.g. the asset had been removed from the pool, or the project file was hand-edited). If the clip's source genuinely had no audio track, FFmpeg would fail the entire `-filter_complex` graph trying to map a non-existent stream. **Fixed**: `_clip_has_audio()` now falls back to probing the file directly (`core.media_probe.probe_file`) when no pool asset matches, defaulting to `False` (silent, not a crash) if even that fails.
- **The "two-pass" export setting was inert.** `ExportSettings.two_pass` existed as a dataclass field but was never read anywhere in `Exporter.export()`, and the export dialog didn't even expose a control for it. **Fixed**: implemented real two-pass, target-file-size encoding — `Exporter._export_two_pass()` computes a video bitrate budget from a target size in MB and the project duration, then runs an FFmpeg analysis pass (video only, discarded output) followed by the real encode pass at that bitrate. `ui/export_dialog.py` gained a "Two-pass, target file size" checkbox and an MB field.
- **Importing media froze the UI.** `MainWindow.import_media_paths()` ran `probe_file()`/`generate_thumbnail()`/`generate_waveform()` synchronously in a loop on the UI thread, papering over the freeze with `QCoreApplication.processEvents()` — a batch of large files would visibly hang the app. **Fixed**: the work now runs in `ui/import_worker.py::ImportWorker` on its own `QThread` (the same pattern the export dialog already used), with a status-bar progress bar; the main thread only handles the final `Project`/UI updates via signal handlers.
- **No feedback for missing media.** Importing a path that no longer exists, or opening a `.vproj` referencing moved/deleted files, failed silently. **Fixed**: `ImportWorker` now checks `os.path.isfile()` before probing and reports a clear per-file error instead of mis-probing a nonexistent path; `MainWindow.open_project()` now warns (listing up to 10 paths) if any media in the loaded project's pool can't be found on disk.
- **Closing the export dialog while FFmpeg was still running could destroy a live `QThread`.** `ExportDialog.closeEvent()` cancelled and waited only 3 seconds for the render thread before closing regardless of whether FFmpeg had actually exited. **Fixed**: `Exporter.cancel()` now terminates the FFmpeg subprocess immediately (stored as `self._process`) instead of waiting for the run loop to next notice a cancellation flag between progress lines; `closeEvent()` now refuses to close (with a message asking the user to wait) if the thread still hasn't stopped after 5 seconds, rather than destroying it mid-flight.
- **No overwrite confirmation on export.** Picking an existing output filename silently replaced it. **Fixed**: `ExportDialog._on_export()` now asks for confirmation first.
- **No crash recovery.** A crash mid-edit lost all unsaved work, with no autosave of any kind. **Fixed**: `MainWindow` now autosaves the current project to a dedicated recovery slot (`~/.video_editor/autosave/autosave.vproj`, separate from the user's actual project file) every 2 minutes while dirty, and offers to restore it on the next launch if found; the slot is cleared on a successful save or a confirmed discard, so it never resurrects work the user explicitly saved or threw away.
